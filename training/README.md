# Training and evaluation

Scripts for the AI component: dataset preparation, optional fine-tuning, and
evaluation.

## Provenance of the dataset

The dataset in `datasets/processed/` is **synthetic**. It is generated by
`prepare_dataset.py` from hand-written scenarios. It is not collected from real
meetings. Say so plainly in any write-up; it is a defensible design choice, not
something to hide.

The reason for generating rather than collecting: real meeting corpora (AMI,
ICSI) need licences and data agreements, and recording real meetings raises
consent issues. Generating gives exact supervision - the expected extraction is
known, so nothing is ambiguous - at the cost of realism. The limitations are
described in `datasets/README.md` and must appear in the report.

## Scripts

| Script | Purpose |
|---|---|
| `prepare_dataset.py` | Generate the synthetic transcript -> minutes dataset |
| `train.py` | LoRA fine-tuning of the extraction model (optional) |
| `evaluate.py` | Measure WER, precision/recall/F1, ROUGE, field accuracy |

## Quick start

```bash
cd backend && source .venv/bin/activate && cd ..
python training/prepare_dataset.py
python training/evaluate.py --split test
```

## Fine-tuning is optional

The system works without fine-tuning. It uses a pretrained model plus the
rule-based extractors. Fine-tuning is an experiment to see whether a small
domain-specific adapter improves the structured-extraction fields. If it does
not measurably help, say so in the report - a negative result reported honestly
is worth more than an unverified claim.

### What is trained, and what is not

| Component | Origin | Trained by us? |
|---|---|---|
| Speech recognition (faster-whisper) | Pretrained on a large public corpus | No |
| Text embedding for evaluation (MiniLM) | Pretrained | No |
| Base extraction model (Qwen2.5-0.5B-Instruct) | Pretrained | No |
| LoRA adapter on the extraction model | Trained on our synthetic dataset | **Yes (optional)** |
| Extraction prompt, schema and validators | Written for this project | n/a - not learned |
| Deterministic rule layer | Written for this project | n/a - not learned |
| MoM renderer and exporters | Written for this project | n/a - not learned |

This separation is the honest answer to "which part is the AI you trained?".
The speech model and the language model are pretrained. What this project
contributes is the task definition, the dataset, the grounding and validation
logic, the deterministic rules for the fields a language model handles badly,
and an optional adapter.

### Why LoRA rather than full fine-tuning

Full fine-tuning updates all ~495M weights and keeps optimizer state for each,
which a 16 GB machine cannot do comfortably. LoRA freezes the base weights and
trains small low-rank matrices beside the attention projections. In this
project only **1.08M of 495M parameters (0.22%)** are trainable, and the
resulting adapter is a few megabytes.

```bash
# Prove the mechanism works in a few minutes (4 steps wired to a tiny subset)
python training/train.py --max-steps 4 --limit 8 --grad-accum 2

# A more real run (~tens of minutes on CPU)
python training/train.py --max-steps 120 --limit 200

# With a CUDA GPU
python training/train.py --max-steps 200 --device cuda
```

The adapter is written to `models/mom-lora/`. To use it, point
`MMA_EXTRACTION_ADAPTER_PATH` at that directory and re-run the evaluation.
Compare the two runs before claiming it helped.

Measured on a CPU-only machine during development: 4 steps over 8 examples
took about 3 minutes, with training loss falling from 0.44 to 0.23 and
validation loss from 0.43 to 0.37. That is evidence the machinery learns, not
evidence that it improves the downstream fields - only the evaluation can
show that.

## Evaluation

```bash
# Deterministic rule layer only - fast, no model download
python training/evaluate.py --split test --method rules --no-semantic

# Full pipeline: language model plus rules
python training/evaluate.py --split test --method hybrid --no-semantic
```

The two runs answer different questions. `rules` measures the deterministic
layer in isolation, so a change there is visible immediately. `hybrid` measures
what the deployed system actually does, including the language model's
contribution and its mistakes.

Metrics, and why each is used:

| Metric | Applies to | Why |
|---|---|---|
| WER | Transcription | The standard ASR error measure; word-level edit distance over the reference |
| Precision / recall / F1 | Decisions, discussion points, participants, action items | Set comparison, so a repeated item is not counted twice |
| Field accuracy (person, deadline) | Action items | Graded only where the task was matched, isolating attribution errors from detection errors |
| ROUGE-L | Overview, conclusion | Overlap with the reference wording; a proxy, and a weak one for paraphrase |
| Semantic similarity | Overview, conclusion | Catches correct paraphrase that ROUGE misses (needs `sentence-transformers`) |

`--no-semantic` skips the embedding model. Use it on a machine without the
model cached, or when you only need the set-based numbers.

### Reporting the numbers honestly

The test split is 16 examples drawn from the same six scenarios as training,
paraphrased. It measures whether the system learns the task and the output
schema, and whether the rule layer generalises across wording. It does **not**
measure performance on real, messy meeting audio. State that limitation next to
any number quoted from this split.
