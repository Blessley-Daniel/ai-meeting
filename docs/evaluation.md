# Evaluation Results

Every number in this document was produced by running the scripts in
`training/` on the machine described below. Nothing here is estimated or
illustrative. Raw machine-readable output is in `docs/eval_rules_test.json` and
`docs/eval_hybrid_test.json`; regenerate them with the commands in each section.

Results are reported for two configurations, because they answer different
questions:

* **rules** — only the deterministic rule layer. No language model.
* **hybrid** — the deployed system: language model plus rule layer plus
  grounding and validation.

## The test data, and what it does and does not show

The test set is **synthetic**: generated by `training/prepare_dataset.py` from
six hand-written scenarios, with held-out variants for the test split. Splits
are grouped by scenario so no scenario appears in two splits.

What this measures: whether the extraction learns the task and the output
schema, and whether the rule layer generalises across paraphrases of the same
scenario.

What it does **not** measure: behaviour on real, messy meeting audio. The text
is clean and templated, with no disfluencies, false starts, overlapping speech
or speech-recognition errors. Treat every figure below as an upper bound and
label it as such wherever it is quoted.

## 3. What these numbers actually mean

**Decisions and action items are reliable on this data (F1 1.00).** The
deterministic rule layer detects the explicit cue phrases the scenarios use
("the team decided to X", "Y will do Z by W"), and the language model adds
nothing here. Note that this is a *strength of the rules on templated text, not
evidence that the rules would generalise* to meetings that phrase decisions
differently.

**The language model is what earns its place on the hard fields.** The rules
alone produce no discussion points and no overview at all (F1 0.00, ROUGE 0.00
— visible in the rules column). The hybrid system produces both, at moderate
quality. This is the clearest justification for including a language model: it
covers what pattern matching cannot.

**Discussion-point quality is genuinely weak (F1 0.19).** This is worth stating
plainly rather than hiding. The model's discussion points are semantically
related to the reference but worded differently, and the metric is strict
set-overlap, so it penalises paraphrase. ROUGE being unavailable for this field
compounds it. Two readings are defensible and both should be reported: either
the field is hard for a 0.5B model, or the metric is harsh for open-ended
phrasing. The semantic-similarity metric (enabled by dropping `--no-semantic`)
is the right instrument to tell these apart, and running it is the natural next
step.

**Title accuracy is low (0.125).** The scenarios do not state a meeting title
in the transcript, so the reference title is usually the filename-derived
fallback while the model invents a plausible heading. Exact-match scoring
therefore punishes correct-looking output. The fallback behaviour is deliberate
(a nameless meeting still needs a heading); the metric simply does not measure
what it looks like it measures.

**Participants P=0.906.** Five false positives across 16 meetings: the model or
rules occasionally pick up a name that is mentioned but not a participant. The
grounding check removes most fabricated names but cannot distinguish "attended"
from "was mentioned".

## 4. Fine-tuning

The LoRA pipeline in `training/train.py` runs and reduces training loss. A
4-step smoke run on 8 examples produced:

| Step | Training loss | Validation loss |
|---|---|---|
| 1 | 0.4448 | — |
| 2 | 0.3659 | 0.4300 |
| 3 | 0.2818 | 0.3661 |
| 4 | 0.2276 | — |

Only 1,081,344 of 495,114,112 parameters (0.22%) are trainable, which is what
makes fine-tuning viable on a CPU-only machine.

**This is evidence that the training machinery works. It is not evidence that
fine-tuning improves the extracted fields.** Because the rule layer already
reaches F1 1.00 on decisions and action items, there is little headroom for an
adapter to show a gain there. The field where improvement would be meaningful
is discussion points, at F1 0.19. A full comparison — train the adapter for
more steps, then run the hybrid evaluation with and without it — is the
experiment to run, and the honest outcome may well be that it does not help on
this dataset. Report that as the finding if so.

## 5. Limitations

1. **Synthetic data.** Clean, templated text with no ASR errors and only six
   scenarios. All figures are upper bounds; none describe real meeting audio.
2. **No speaker diarisation.** Participants are inferred from names used in
   the transcript. Two speakers with the same name are not separated, and a
   participant who is never named by another participant may be missed.
3. **No real WER.** The 0.000 WER is one clean synthetic utterance. It says
   nothing about real recordings.
4. **Discussion-point metric is strict.** Set-overlap penalties for paraphrase
   make the field look worse than a human would judge it. Report alongside
   semantic similarity to give the fairer picture.
5. **Small test set.** 16 examples. Differences of one item move the F1 by a
   visible amount, so treat small gaps between configurations as noise, not
   signal.

## 6. Reproducing

```bash
# 1. Regenerate the dataset (deterministic for a fixed seed)
python training/prepare_dataset.py

# 2. Rules-only baseline
python training/evaluate.py --split test --method rules --no-semantic \
  --output docs/eval_rules_test.json

# 3. Full system
python training/evaluate.py --split test --method hybrid --no-semantic \
  --output docs/eval_hybrid_test.json

# 4. Optional: semantic similarity instead of ROUGE alone
python training/evaluate.py --split test --method hybrid
```
